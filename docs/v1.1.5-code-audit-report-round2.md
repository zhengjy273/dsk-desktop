## 三、新发现（N27 起）

### N27【中等 · 待实证】N15 的归属判定可能对「缓存命中」响应形态完全不生效

**问题**：`parseHistorySessionId` 与 `parseHistoryAccumulatedTokens` 都先过 `pickBizData`（`src/session/quota-parser.ts:125-142`），而 `pickBizData` **只认** `data.biz_data` / `data.bizData` / 顶层 `biz_data` / 顶层 `bizData` 四种包装，**没有**「顶层直接就是业务体」的兜底。但 `docs/KNOWN-LIMITS.md:136` 把缓存命中的响应记录为：

```
{"chat_session":{…},"chat_messages":[],"cache_control":"MERGE"}   // 398~400 字符
```

这是**顶层** `chat_session`。而「缓存命中」恰恰是 `history_messages` 拿不到 `chat_messages`、最需要按响应体 id 做归属判定的场景（`KNOWN-LIMITS.md:59` 也记了这是「实测常见」）。

**可复现证据**（Node 24 直接 import 纯函数，无需 Electron）：

```bash
# 探针：src/session/quota-parser.ts:562
node -e "import('file:///E:/Work/DSH/deepseek-desktop/src/session/quota-parser.ts').then(m=>{
  const id='11111111-1111-4111-8111-111111111111';
  console.log(m.parseHistorySessionId(JSON.stringify({chat_session:{id},chat_messages:[],cache_control:'MERGE'})));  // -> null
  console.log(m.parseHistorySessionId(JSON.stringify({biz_data:{chat_session:{id}}})));                            // -> id
})"
```

实测输出：顶层 `chat_session` → `null`；`{biz_data:{chat_session}}` → `11111111-…`。若真实响应确为文档字面形态，则 `belongs` 永远走 `respConv === null` 的旧分支，**N15 在缓存命中场景原样复发**；同一形态下 `parseHistoryAccumulatedTokens` 也返回 null（此时靠 `quota-store` 的按会话缓存兜底，用户不易察觉）。

**判定依据的两面**：
- 反证：若真实响应无 `biz_data` 包装，`parseHistoryAccumulatedTokens` 从 v1.1.1 起就永远拿不到 token，与实测「切换会话能看到已用量」矛盾 → 更可能文档 `:136` 是**内层结构的简写**。
- 但文档是仓库里唯一的形态记录，且 398~400 字符与「完整包装 + 空消息」也吻合；**不能靠推理定案**。

**建议（二选一，都很快）**：
1. 用现成诊断开关抓一次真实响应：`DSK_QUOTA_DEBUG=1` 时 `handleQuotaJson` 会把 history 响应前 400 字符打进日志（`src/main/main.ts:1512-1518`）。确认一次缓存命中的 body 是否带 `data.biz_data`。
2. 或在 `parseHistorySessionId` 里加顶层兜底（不必改 `pickBizData`，避免影响 token 解析口径）：

```ts
const parsed = safeJsonParse(raw);
const bizData = pickBizData(parsed);
const session = isRecord(bizData) ? bizData['chat_session']
  : isRecord(parsed) && isRecord(parsed['chat_session']) ? parsed['chat_session'] : null;
```

并补一条单测：顶层 `{chat_session:{id},chat_messages:[],cache_control:'MERGE'}` 必须能取到 id。

### N28【低】`belongs` 是大小写严格比较，UUID 大小写不一致会静默丢弃有效数据

**问题**：`parseHistorySessionId` 只 `trim()`、不规范化大小写（`src/session/quota-parser.ts:568-571`），实测传入大写 UUID 会**原样返回** `B8D3A040-…`；而 `belongs` 用 `pageConv === respConv` 严格比较（`src/main/main.ts:1543-1546`）。页面 URL 里的 id 由站点生成（实测全小写），响应体 id 若某天变大写，`belongs` 恒 false → `!belongs` 提前 return → **该会话的 token/次数被静默丢弃且不落盘**。

**证据**：探针 `parseHistorySessionId(JSON.stringify({biz_data:{chat_session:{id:'B8D3A040-…'}}}))` → 返回大写原样；`extractConversationId`（`src/session/deepseek-mirror.ts:30-47`）只做 `SAFE_ID` 校验，不改大小写。

**建议**：`parseHistorySessionId` 返回 `trimmed.toLowerCase()`（会话 id 是 UUID，大小写不承载信息）；或 `belongs` 比较时两边 `.toLowerCase()`。同时补一条单测。

### N29【低】`setWindowOpenHandler` 对 `about:blank` 会调用 `onExternal`，与 `blockOffsite` 不一致

**问题**：`blockOffsite` 显式放行 `u === 'about:blank'`（`src/main/content-view.ts:116`），但 `setWindowOpenHandler` 只判 `isSameSiteUrl`（`:95-98`）→ `window.open('about:blank')` 会走 `shell.openExternal('about:blank')`（`main.ts:342` 处 catch 掉，不会崩，但在 Windows 上可能弹「选择打开方式」或静默失败）。**这不是本轮引入的回归**（旧代码 `!url.startsWith(siteOrigin)` 同样为真），但两处放行策略应统一。

**建议**：handler 里一并放行 `about:blank` / `about:srcdoc`；`onExternal` 入口再加一道 `http(s):` 协议白名单（更稳，`shell.openExternal` 对任意 scheme 都敏感）。

### N30【低 · 未来升级风险】`will-redirect` 依赖 deprecated 的位置参数 `isMainFrame`

**问题**：`src/main/content-view.ts:122-124` 用 `(e, url, _isInPlace, isMainFrame)`。Electron 44.7.0 的签名是 `(details, url /*deprecated*/, isInPlace /*deprecated*/, isMainFrame /*deprecated*/, …)`（`node_modules/electron/electron.d.ts:24826-24854`），新写法是 `details.url` / `details.isMainFrame`。当前可用，但一旦上游移除位置参数，`isMainFrame` 变 `undefined` → `=== false` 不成立 → 子帧 3xx 又被拦（N26 回归，静默、无报错）。

**建议**：改用首参对象，并按可信度保守判断：

```ts
wc.on('will-redirect', (details) => {
  if (details.isMainFrame === false) return;
  blockOffsite(details, String(details.url));
});
```

同理 `will-navigate` 也可一起迁移（现在 `blockOffsite` 直接当监听器，`(e, url)` 位置参数同样是 deprecated 形态）。

### N31【低】`isErrorPageUrl` 严格相等不含 query，而错误页 URL 一定带 query

**问题**：`errorPageUrl` 是 `pathToFileURL(errorPagePath).href`（`src/main/content-view.ts:110-112`），但 `showErrorPage` 生成的地址是 `file://…/error.html?code=…&desc=…&retry=…`（`src/main/content-view.ts:315-329`）。因此 `isErrorPageUrl` 对**实际加载的错误页 URL 恒为 false**。当前无实害：错误页由 `loadURL` 程序化加载（不触发 `will-navigate`），`error.html` 里只有「重试」按钮跳 `retry`（站内 URL，由同源判断放行），没有指向自身的导航。但语义上「只放行错误页本身」这道闸门对真正带 query 的错误页是失效的。

**建议**：`u === errorPageUrl || u.startsWith(errorPageUrl + '?')`；或解析成 URL 后比 `origin + pathname`。

### N32【低】`rememberNormalBounds` 未排除 `mini` 状态，`lastNormalBounds` 会被迷你窗尺寸污染

**问题**：`main.ts:432-442` 只过滤最小化/全屏/最大化与异常值（宽高 < 200、坐标 < -10000）。但迷你窗是 380×520（> 200），且 `applyMiniBounds` 的 `win.setBounds(...)`（`:613-619`）与用户拖动迷你窗都会触发 `resize` / `move` 事件 → `rememberNormalBounds` 把 `lastNormalBounds` 覆盖成「迷你窗的外框/位置」，违背它自己的注释语义（`:230-237`「最近一次**正常状态**的窗口 bounds」）。

**为什么当前没出事**：`setMini(true)` 时先 `normalBounds = lastNormalBounds ?? win.getBounds()`（`:629`），退出迷你窗用 `normalBounds` 优先（`:651`），所以恢复尺寸正确；`applyMiniBounds` 也优先 `lastNormalBounds`（`:615`）——而迷你期间它的值恰好等于当前迷你尺寸，算出的 x/y 仍是「原地」，视觉上无差。属于**语义污染而非可观察 bug**。

**建议**：`rememberNormalBounds` 开头加 `if (mini) return;`（一行），把 `lastNormalBounds` 的语义真正守住，避免将来加「记住上次普通窗口位置」功能时踩坑。

### N33【低】N19 反向检测用 `id in entries`，对 `__proto__` 等原型链键漏检

**问题**：`src/store/quota-store.ts:170-173`：

```ts
for (const id of Object.keys(rawEntries)) { if (!(id in entries)) return true; }
```

`entries` 是普通对象字面量（`:184` `const entries: Record<string, SessionTokenEntry> = {}`），`in` 会查原型链。实测 `'__proto__' in {}` === `true`；而 `JSON.parse('{"entries":{"__proto__":{…}}}')` 会生成**own** `__proto__` 键（`Object.keys` 能枚举到）。因此磁盘上这个无效条目永远不会触发 repair。它确实会被 `parseSessionTokensFile` 丢弃（`:186` 的 `isSafeAccountId('__proto__')` 为 false，`SAFE_ID` 要求首字符 `[A-Za-z0-9]`），所以后果只是「该残留条目永久留盘」，不会误删数据。

**建议**：`if (!Object.prototype.hasOwnProperty.call(entries, id)) return true;`。同一函数正向前向循环里的 `rawEntries[id]` 取值也可换成 own-property 读取，进一步收紧。

---

### N34【观察 · 前向兼容】反向检测在「旧版本读新版本缓存」时会删掉未来新增的条目类型

**问题**：`parseSessionTokensFile` 只认 `tokens` / `regenerateUsed` / `editUsed` 三字段，三字段全缺即丢弃（`src/store/quota-store.ts:186-206`）。N19 的反向检测会把「被丢弃」的条目标记为需要 repair，随即 `saveSessions` 回写**删除**它们。若将来 v1.1.6 给 `SessionTokenEntry` 加字段（例：`lastSeenAt`），而用户回退到 v1.1.5 运行一次，旧版本会把新字段条目判为「无效」并删掉。自用单机、单向升级为主，风险极低，仅作记录；若在意，可在 parse 里对「含未知字段但 updatedAt 正常」的条目保留（而不是丢弃）。

## 四、lead 重点清单逐条回答

1. **N15 `!belongs` 提前 return 是否跳过本应发生的 refresh/其他副作用？**
   不跳过。`handleQuotaJson` 的 `changed` 只在本分支内置 true（`main.ts:1537-1580`），函数末尾的 `if (changed) refreshQuotaView()` 本就不该为「不属于当前会话的响应」执行；`return` 前也没有别的清理动作。唯一副作用是「该响应的 tokens/usage 不更新内存」——这是修复的目的。

2. **`targetConv`，在 `pageConv !== sessionTokensFor`（刚切会话）时会不会写错会话？**
   不会。`belongs === true` 时只有两种可能：`respConv === pageConv`（写响应体 id，权威）或 `respConv === null`（退回旧口径，写 `sessionTokensFor`）。`onNavigated` 尚未把 `sessionTokensFor` 更新到新会话的那个瞬间，`respConv` 已经指向新会话，所以落盘目标是**响应所属会话**，不是旧值。`setSessionTokens`/`setSessionActions` 内部还有 `isSafeAccountId` 二次校验（`quota-store.ts:276, 317`），非法 id 只会静默不落盘，不会污染文件。

3. **`parseHistorySessionId` 对 biz_data 直接形态 / 空 body / business 码非 0 的处理？**
   实测（Node 24 直接 import，2026-11-17）：

   | 输入 | 结果 |
   |---|---|
   | `{code:0,data:{biz_code:0,biz_data:{chat_session:{id}}}}` | id ✅ |
   | `{code:0,data:{biz_data:{chat_session:{id}}}}` | id ✅ |
   | `{biz_data:{chat_session:{id}}}`（顶层 biz_data） | id ✅ |
   | `{chat_session:{id}}`（顶层业务体，无包装） | **null**（N27） |
   | `code:1` / `biz_code:1` | null ✅ |
   | `''` / `'{}'` / `'<html>'` / `'null'` / `'[]'` | null ✅ |
   | `chat_session:null` / `biz_data:[]` / 数字 id / `'too-short'` / 31 字符 | null ✅ |
   | 32 字符 id | 返回（边界按 `>= 32`） |
   | id 前后带空格 | trim 后返回 ✅ |
   | 大写 UUID | **大写原样返回**（N28） |

4. **单测覆盖是否够？**
   不够充分，缺三类：① 顶层 `chat_session` 形态（N27）；② 大小写（N28）；③ 与 `belongs` 的联合矩阵——`belongs` 内联在 `handleQuotaJson`（`main.ts:1543-1546`），无法单测。建议把判定抽成纯函数，例如
   `isHistoryResponseForPage(pageConv, respConv, sessionTokensFor): boolean`，补 8 组组合（R=P / R≠P / R=null&三种 pageConv 状态 / 空串），这是上一轮报告就建议过、本轮仍未做的「坑 32 残留」。

5. **N16：`isSameSiteUrl` 的边界？**
   实测全表（Node 24，直接 import `brand.ts`）：

   | 输入 | 结果 | 判读 |
   |---|---|---|
   | `https://chat.deepseek.com/`、`/a/chat/s/abc`、`?x=1#y`、`/../x` | true | 路径/查询/hash/相对段均不影响 ✅ |
   | `https://CHAT.DeepSeek.COM/x`、`HTTPS://…` | true | URL 规范化处理大小写/协议 ✅ |
   | `https://chat.deepseek.com:443/x` | true | 默认端口被规范化掉 ✅ |
   | `https://chat.deepseek.com:8443/x` | false | ✅ |
   | `http://chat.deepseek.com/x` | false | ✅ |
   | `https://chat.deepseek.com.evil.com/x` | false | ✅ 原始漏洞已封 |
   | `https://chat.deepseek.com@evil.com/x` | false | userinfo 混淆也挡住 ✅ |

   | `https://chat.deepseek.com./x`（FQDN 尾点） | false | 理论上与站点等价，但浏览器自身不会产生；仅记录 |

   单测 `tests/unit/brand.test.ts:4-33` 覆盖了路径/前缀攻击/端口/协议/非 http/自定义 origin/尾斜杠，**未**覆盖大写 host 与默认端口（实现正确，属覆盖补强建议）。

6. **`errorPageUrl` 为 null 时的行为？**
   `isErrorPageUrl` 恒 false（`:113`），此时 `blockOffsite` 仍放行站内与 `about:blank`，其余 `file:` 一律 `preventDefault` + 外跳。`main.ts:336-345` 实际总会传 `ERROR_PAGE_PATH`，所以生产路径不会是 null；该分支只是防御性正确。

7. **`will-redirect` 主框架参数在 Electron 44 的类型/运行语义？**
   44 上第 4 个位置参数仍传入且语义正确（`deprecated` 标记），代码 `isMainFrame === false` 早退成立；新 API 是 `details.isMainFrame`。当下无缺陷，见 N30 的升级风险。

8. **`setWindowOpenHandler` 对站内 `about:blank` 的行为是否变化？**
   **未变化**：旧代码 `!url.startsWith(SITE_ORIGIN)` 对 `about:blank` 同样为真 → 同样会 `onExternal`。所以不是本轮回归；但两处放行策略不一致（N29）。

9. **BUG-4：`lastNormalBounds` 语义变外框后，所有读取点是否一致？**
   一致，逐点核对：
   - 写入：`rememberNormalBounds` 用 `win.getBounds()`（`:439`，外框）；
   - 迷你基准：`applyMiniBounds` 的 `base.x/y/width/height` 来自 `lastNormalBounds / normalBounds`，再 `win.setBounds`（`:613-619`，外框）；
   - 进入迷你：`normalBounds = lastNormalBounds ?? win.getBounds()`（`:629`，外框）；
   - 退出迷你：`back = normalBounds ?? lastNormalBounds` → `win.setBounds(back)`（`:651-652`，外框）；
   - 默认兜底 `{80,80,1180,820}`（`:615`）与 `createWindow` 的 `width/height`（`:327-328`，BaseWindow 的 width/height 即外框）一致。
   结论：**主进程内部全部统一为外框语义**，BUG-4 的「每进出一次内容区缩一圈」不再成立。

10. **`self.miniBounds` 仍 `getContentBounds` 会不会让日志/自检混淆？**
    不会混淆，但要看用途：`self.miniBounds`（`:669`）、`self.windowBounds`（`:540`）、`self.miniBoundsAfterUnmaximize/AfterLeaveFullScreen/AfterRestore`（`:494, 501, 525`）都是**内容区**，供运行期自检与 `docs/m1-evidence/t1-selftest.json` 使用；selftest 的容差与注释明确按内容区写（`:1921-1926` 记录「380×520 外框 → 367×485 内容区」）。主进程内部窗口基准（外框）与自检证据（内容区）用途不同、互不混用，**未受影响**。可选改进：在证据字段旁注明「内容区」以免后来者误当外框。

11. **selftest 的 `miniBoundsAfter*` 是否受影响？**
    不受影响（仍读内容区、容差 300–500 / 400–650）。但要提醒：容差 ±100 像素**掩盖得住** BUG-4 那种「一个标题栏约 13px」级别的漂移——即上一版自检对 BUG-4 是**测不出来**的。若要防回归，加一条严格断言：`setMini(false)` 之后的 `win.getBounds()` 与进入前的 `getBounds()` 逐字段相等（或容差 ≤2px）。这同时补强 N25（自检无 v1.1.5 新机制断言）。

### 8.2 新发现（N35 起）

#### N35【中 · 未来兼容】N30 的 details 分支检测位置错，升级 Electron 后主框架 3xx 会被系统性阻断

**问题**：`src/main/content-view.ts:127-138` 从 **`args[1]`** 判断"是否是 details 对象"：

```ts
const second = args[1];
const details = typeof second === 'object' && second !== null && 'url' in (second as object)
  ? (second as {...}) : null;
const target = details ? String(details.url ?? '') : String(second ?? '');
const isMain = details ? details.isMainFrame !== false : args[3] !== false;
```

而 Electron 的实际签名（`node_modules/electron/electron.d.ts:17981`）是 details 在**第一位**：

```
on(event: 'will-redirect', listener: (details: Event<WebContentsWillRedirectEventParams>,
                                      url /* @deprecated */,
                                      isInPlace /* @deprecated */,
                                      isMainFrame /* @deprecated */, …))
```

且 `type Event<Params> = { preventDefault; defaultPrevented } & Params`（`electron.d.ts:16`）——**44 上的 `args[0]` 本身就含 `url` / `isMainFrame`**，所以正确写法应该是检查 `args[0]`，而不是 `args[1]`。

**可复现**（等价逻辑探针，2026-11-17 本机 Node 24 实跑）：

```
Electron44 现状 (details,url,isInPlace,isMainFrame) => target= "https://chat.deepseek.com/a" isMain= true    ✅
Electron44 子帧                                    => target= "https://ads.example/x"        isMain= false   ✅
未来 details-only（url/isMainFrame 已移除）         => target= ""   isMain= true   ← 会 preventDefault 空 URL
```

即：**现在（44）走的是位置参数分支，行为正确；注释声称的"新版 details 分支"永远不会命中**。一旦上游移除 deprecated 位置参数（Electron 每次大版本都会废弃一批），`args[1]` 变 `undefined` → `target = ''`、`isMain = true` → `blockOffsite(evt, '')` 判为站外 → **站点自身所有主框架 3xx 被 `preventDefault`**（比原来的 N26「子帧误弹浏览器」严重：站点跳转会整体失效），同时 `onExternal('')` 被 catch 吞掉。

**同类未覆盖点**：`wc.on('will-navigate', blockOffsite)`（`content-view.ts:123`）直接把 `blockOffsite` 当监听器，依赖 `args[1]` 的 url；同一升级下 `String(undefined)` → `'undefined'` → 同样拦掉全部主框架导航。

**建议（3 行改法，两种 API 都成立）**：

```ts
const first = args[0] as { url?: unknown; isMainFrame?: unknown } | undefined;
const details = first && typeof first.url === 'string' ? first : null;
const target = details ? String(details.url) : String(args[1] ?? '');
const isMain = details ? details.isMainFrame !== false : args[3] !== false;
// will-navigate 同样包一层，别把 blockOffsite 裸交给事件
wc.on('will-navigate', (...a: unknown[]) => {
  const d = a[0] as { url?: unknown } | undefined;
  const u = d && typeof d.url === 'string' ? d.url : String(a[1] ?? '');
  blockOffsite(a[0] as Electron.Event, u);
});
```

#### N36【低】业务失败（`code≠0`）但顶层带 `chat_session` 时仍被视为有效归属

**问题**：`parseHistorySessionId` 先 `pickBizData`（`code`/`biz_code` 非 0 → null），再从**顶层** `chat_session` 兜底（`quota-parser.ts:570-572`）。因此 `{code:1, chat_session:{id}}` 仍会返回 id——业务失败响应参与了归属判定，语义不洁。

**实测**：`code:1 + 顶层 chat_session => 11111111-…`（返回 id）；`code:1` + wrapped 形态 → null。

**影响**：`tokens` 与 `usage` 此时都解析为 null，`changed` 不会置 true，**无实害**；仅"失败响应不该当归属依据"的口径问题。若在意，可在 `parsed.code`/`biz_code` 明确非 0 时直接返回 null（不看顶层）。附带一个小形态：`wrapped` 是空 record 时 `wrapped ?? topLevel` 不会回退（实测 `{data:{biz_data:{chat_session:{}}}, chat_session:{id}}` → null），现实中不存在，记录备查。

#### N37【低】`miniRoundTripBoundsStable` 的假失败场景：自检自身会移动窗口

**问题**：`runMainSelftest` 用 `outerBeforeMini = win.getBounds()`（`main.ts:1909`）做基准，但 `setMini(true,true)` 内部的恢复目标是 `normalBounds = lastNormalBounds ?? win.getBounds()`（`main.ts:632`），退出时 `win.setBounds(normalBounds)`（`:654-655`）。若自检触发时 `lastNormalBounds` 与当前 bounds **不一致**（例：窗口处于最大化/全屏——`rememberNormalBounds` 在 `main.ts:436-439` 会跳过记录，`lastNormalBounds` 停留在更早的值；或用户手动 `setBounds` 后事件未落到 `rememberNormalBounds`），往返结束后窗口会被恢复到**旧的** `lastNormalBounds`：

- `miniRoundTripBoundsStable` 判 false → **自检假失败**；
- 同时把用户窗口真的挪到旧位置。

**建议**：自检开始处记下并清空 `lastNormalBounds`（`const saved = lastNormalBounds; lastNormalBounds = null;`），往返后比较再还原；或在比较前 `await` 一次 `resized`，并额外断言 `normalBounds` 与 `outerBeforeMini` 一致。

#### N38【极低】正向循环的 `rawEntries[id]` 仍可能取到原型链成员

**问题**：`quota-store.ts:156` `const rawEntry = rawEntries[id];`——当 `entries` 含 own 键 `constructor`（`isSafeAccountId` 允许，首字符是字母）而磁盘 raw 里没有该 own 键时，会取到 `Object.prototype.constructor`（函数）→ `!isRecord` → 多触发一次 repair。**不丢数据**（只是多写一次盘），与 N33 对称性也差。

**建议**：同一条循环里改 `Object.prototype.hasOwnProperty.call(rawEntries, id) ? rawEntries[id] : undefined`。
